# Content intake
Ask only unanswered consequential questions, at most three together. Reuse prior explicit answers.
1. What question should this explanation answer, for whom, and what should they understand afterward?
2. Which situations matter: initial setup, ongoing operation, direct requests, scheduled work, missing facts or unavailable access? Do not impose these on unrelated subjects.
3. One view or several? Agree on the count and purpose, then the actual content of EACH view and the requested static/interactive scope.

Present a plain-language outline per view covering meaningful actors/actions, inputs, decisions, read/save destinations, outputs and waits. Describe what happens, not just proposed headings or styling. Separate live capability, planned behavior and uncertainty. Confirm the content before drawing a complex new view.

Track: view | question | content confirmation | SVG version | visual approval. An exact approved outline is sufficient; do not ask again. For a small edit, confirm only changed scope if necessary. A user can explicitly waive a checkpoint; time elapsed is never approval.

Regression cases: “what exactly does the weekly task do?” needs an actual action list; “first use” cannot be hidden behind “load settings”; agreeing to tab labels does not approve the content inside them. Follow the main skill for subsequent SVG and interactive checkpoints.
